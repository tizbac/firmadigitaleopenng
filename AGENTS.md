# AGENTS.md

C++17/Qt6 digital-signature tool: PAdES-BES PDF signing, P7M (CMS detached) sign/verify, TSL verification, PKCS#11 (Bit4id) token access. `fdo_core` is a Qt-free static crypto library; the Qt GUI (`main.cpp`, `mainwindow.*`, `pdfpreview.*`) sits on top. Everything lives in namespace `fdo`. README.md has full details.

## Build & test

```
cmake -S . -B build && cmake --build build -j
ctest --test-dir build --output-on-failure          # all suites
ctest --test-dir build -R pades --output-on-failure  # single suite
```

- Requires Qt6 >= 6.5 (Widgets/Network/Sql), OpenSSL 3, libxml2, and `libpoppler-qt6-dev`. Poppler ships no CMake config; CMakeLists.txt builds an imported target from the raw header/library and fails hard without it.
- **Docker (Debian trixie, hermetic and reproducible):** `docker build --target test -t fdo-test .` runs configure + full build + all 6 ctest suites (Qt 6.8, OpenSSL 3.5, poppler-qt6, SoftHSM2 + OpenSC so the `pkcs11`/`guisign` suites run the real emulated-token path). `docker build -t fdo-pkg .` additionally runs cpack; the `.deb` bundles `libbit4xpki.so` when it is present next to the repo (it is part of the build context, just like on the host) and skips the token module with a WARNING otherwise. `docker run --rm -v "$PWD:/out" fdo-pkg` drops `firmadigitaleopen_<version>_<arch>.deb` into `$PWD`. Container sets `QT_QPA_PLATFORM=offscreen` (tests are headless).
- **Docker (Fedora 44, RPM):** the same Dockerfile also defines `rpm-test` (`docker build --target rpm-test -t fdo-rpm-test .` → build + 6 ctest on Fedora, Qt 6.11 + poppler-qt6 + SoftHSM at `/usr/lib64/pkcs11/libsofthsm2.so`) and `rpm-pkg` (`docker build --target rpm-pkg -t fdo-rpm .` + `docker run --rm -v "$PWD:/out" fdo-rpm` → `firmadigitaleopen-<version>-1.<arch>.rpm`). The Dockerfile default target is still the Debian `package` stage.
- **Docker (AppImage):** `docker build --target appimage -t fdo-appimage .` (builds on the Debian `test` stage) runs linuxdeploy + the Qt plugin (`ENV APPIMAGE_EXTRACT_AND_RUN=1` so linuxdeploy can spawn the plugin AppImage without FUSE; a `qmake6` symlink is added so the plugin finds Qt; the Debian build is configured with `-DCMAKE_INSTALL_PREFIX=/usr` so the DESTDIR install lands under `$APPDIR/usr/...`). Output `FirmaDigitaleOpen-x86_64.AppImage` carries the binary, Qt6/poppler/ssl/xml2 libs, the platforms plugin and the Bit4id bundle at `usr/lib/<multiarch>/firmadigitaleopen/`; `defaultP11Lib()` probes `$APPDIR/usr/lib/x86_64-linux-gnu/firmadigitaleopen/libbit4xpki.so` then `$APPDIR/usr/lib/...` before the system paths.
- **Docker (Windows x64):** `docker build --target win-package -t fdo-win .` cross-compiles with Fedora 44 `mingw64-*` packages (Qt 6.11, poppler-qt6, OpenSSL, libxml2) using `cmake/toolchain-mingw64.cmake`, then packages the staged `cmake --install` tree with native NSIS on Debian. `docker run --rm -v "$PWD:/out" fdo-win` drops `firmadigitaleopen-<version>-win64-setup.exe` into `$PWD`. The Debian `package` stage stays last, so the default `docker build .` still produces the `.deb`.
- **Windows runtime DLLs:** `packaging/windows/deploy.sh` computes the PE import closure with `objdump` and copies every non-system DLL from the mingw sysroot plus the needed Qt plugins (`platforms`, `styles`, `tls`, `sqldrivers`, `networkinformation`) next to the exe — this replaces `windeployqt` (Fedora's cross Qt does not ship it). It fails the build on a missing DLL, so a green build means the bundle is complete.
- **Windows Bit4id module:** `bit4xpki.dll` (official Bit4id **x86-64** PKCS#11 module, version 1.4.11.1228, extracted from the Bit4id Universal Middleware kit) is committed next to the repo together with `bit4xpki.dll.conf`, `bit4xpki.dll.vpn.license`, `bit4xpki.dll.rc/*.lic` and the x86-64 companion modules `bit4opki.dll`, `bit4ipki.dll`, `bit4npki.dll`, `bit4extplg.dll` (card-specific backends / extension plugin loaded by the generic module). CMake installs them into the app directory; they must stay together (the module reads its config/licences from its own directory and loads companions from the app dir). The Windows build is 64-bit only, matching these DLLs. `defaultP11Lib()` probes `FDO_PKCS11_LIB`, then `libbit4xpki.dll` next to the exe, then a machine-wide Bit4id install (`%SystemRoot%\System32\bit4xpki.dll`, `%ProgramFiles(x86)%\Bit4Id\Universal MW\etc`), then the self-contained bundled `bit4xpki.dll`, then OpenSC. Preferring a machine-wide vendor install is deliberate: it ships the complete runtime/registry configuration. Set `FDO_PKCS11_LIB` to force a specific module. Windows tests are intentionally not built/run (ctest is POSIX/bash-only).
- The checked-in `build/` and `build-plain/` directories are stale: they were configured from a previous checkout path (`/home/tiziano/FirmaDigitaleOpen/firmadigitaleopencpp`), so their ctest entries point at old binaries. Configure a fresh build dir instead of trusting them.
- No lint/format/typecheck tooling is configured in this repo.

## Test suites and gotchas

- Suites: `c14n`, `tslverifier`, `p7mverify`, `pades` (pure, fast); `pkcs11`, `guisign` (need a PKCS#11 module, resolved automatically — see below).
- **`tests/data/test.pdf` is missing from the repo**, but `pades` and `guisign` hard-fail without it (`tst_pades` exits 2). Any small valid PDF works; place it at `tests/data/test.pdf`. The PAdES parser only supports classic xref tables, not xref streams. Test binaries take the data dir as `argv[1]`, so they can also be pointed at any dir containing a `test.pdf` (e.g. `./build/tst_pades /path/to/dir`).
- `pkcs11` and `guisign` run via `tests/run_pkcs11.sh`, which resolves a module in order: (1) `FDO_PKCS11_LIB` + optional `FDO_PKCS11_PIN` env vars (physical token), (2) SoftHSM2 emulator — auto-initialises a throwaway token in a temp dir and exercises full login→sign→verify, (3) Bit4id lib next to the repo for enumeration-only, (4) skip with PASS. A missing token is never a failure; a module-load/ABI error or a signature-verification mismatch is.
- To run the GUI test headless with a physical token: `FDO_PKCS11_LIB=../libbit4xpki.so FDO_PKCS11_PIN=1234 ctest --test-dir build -R guisign --output-on-failure`.
- Optional real-world P7M check: configure with `-DTESTP7M=/path/to/file.p7m` (adds the AgID TSL verification part to `p7mverify` and a real-world smoke run to the `guisign` verify-tab part). **Never commit `.p7m` files** — they contain signed content (`.gitignore` already excludes `*.p7m`).
- The GUI verify tab (accepts signed `.pdf` — embedded PAdES — and `.p7m`) **requires an up-to-date TSL**: no explicit TSL file, no fresh cached one, and (unless disabled) a failed auto-download → the signature is reported NON VALIDA (no self-anchored fallback anymore). TSL resolution order: explicit path in the TSL field → cached copy → auto-download of `https://eidas.agid.gov.it/TL/TSL-IT.xml` into the cache (a "Aggiorna TSL" button forces this). Cache lives under `QStandardPaths::AppLocalDataLocation/TSL-IT.xml`, overridable with `FDO_TSL_CACHE_DIR`; `FDO_DISABLE_TSL_DOWNLOAD=1` turns the auto-download into a no-op (tests rely on it). Trust anchors come **only** from `Tsl::trustAnchors()`: certs of `CA/*` (or `NationalRootCA/*`) services whose status is `granted`, `recognisedatnationallevel` or `accredited`. The TSL XML-signature certificate (`ds:KeyInfo`), withdrawn/ceased services and non-CA services (TSA/eSeal/identity) are deliberately excluded. `P7M::verifyParsed` also rejects an empty anchor vector before chain validation, so the core can never self-anchor. The `guisign` Part C verify-tab test builds its own CA/leaf, signs a fixture P7M AND a real PDF, asserts no-TSL refusal, then caches a fixture TSL containing the CA and asserts positive TSL-anchored verify for both, then replaces it with a withdrawn/KeyInfo-only TSL and asserts refusal again — all hermetic. `tst_pades`/`tst_p7mverify` assert that empty anchors reject a valid signature, and `tst_tslverifier` covers the anchor-filtering rules.
- Run a test binary directly: `./build/tst_pkcs11 <module.so> [pin]`.

## Packaging (CPack .deb)

Build the Debian package from a fresh build dir (do `cmake -S . -B build-deb` then):

```
cmake --build build-deb -j && cpack --config build-deb/CPackConfig.cmake
# -> firmadigitaleopen_<version>_<arch>.deb in the repo root
```

- Content: `/usr/bin/firmadigitaleopen`, the Bit4id bundle under `${libdir}/firmadigitaleopen/` (`libbit4xpki.so` dwm install `install(PROGRAMS ...)` → 755, `.conf` + `.rc/*.lic` 644), plus `firmadigitaleopen.desktop` and `firmadigitaleopen.svg` (hicolor scalable apps). `defaultP11Lib()` in `src/mainwindow.cpp` already probes `/usr/lib/x86_64-linux-gnu/firmadigitaleopen/libbit4xpki.so`, `/usr/lib/...`, `/usr/lib64/...` before the dev-tree variants.
- The `.so`/`.conf`/`.rc` are **in git** (committed deliberately; `.gitignore` re-includes `libbit4xpki.so` over the global `*.so`, and `.conf`/`.rc` are plain tracked files). The module **must** always be installed together with its `.conf` and `.rc/*.lic` in the *same* directory: `libbit4xpki.so` reads `libbit4xpki.so.conf` from its own directory at `C_Initialize` time (strace-verified), so a lone `.so` fails with `CKR_GENERAL_ERROR` (`C_Initialize` rv=5). CMakeLists enforces this: if the `.so` is present but the `.conf` is not, configure fails with `FATAL_ERROR`; if the `.so` is absent the whole bundle is skipped with a WARNING (no orphan config either). Keep the files next to the repo when packaging.
- Debian runtime Depends are set manually (no `dpkg-shlibdeps`): `libqt6widgets6, libqt6network6, libqt6sql6, libpoppler-qt6-6, libssl3, libxml2`. Overridable at configure time via `-DCPACK_DEBIAN_PACKAGE_DEPENDS=...`, and `-DCPACK_DEBIAN_PACKAGE_MAINTAINER=...` for the placeholder maintainer/contact (`firmadigitaleopen@example.invalid`).
- Architecture defaults from `CMAKE_SYSTEM_PROCESSOR` (amd64/arm64); override with `-DCPACK_DEBIAN_PACKAGE_ARCHITECTURE=...`. CMake 4.x derives the output name from `CPACK_PACKAGE_FILE_NAME` (no separate deb-specific name var).
- Inspecting without dpkg: `cd /tmp/i && ar x <file>.deb && tar xzf control.tar.gz && tar tzf data.tar.gz`.
- A `postinst` (from `packaging/postinst`, wired via `CPACK_DEBIAN_PACKAGE_CONTROL_EXTRA`) refreshes `update-desktop-database` + `update-mime-database` on install/upgrade so the file association takes effect immediately.
- File association: `.desktop` MimeType claims **only `.p7m`** (`application/pkcs7-mime` — the non-`x-` variant is what Debian's shared-mime-info globs `.p7m` to — plus `application/x-pkcs7-mime`, `application/pkcs7-signature`, `application/x-pkcs7-signature`). `.pdf` is deliberately excluded so the user's default PDF reader is kept. `Exec=firmadigitaleopen %f` → a path arg makes `main.cpp` call `openFileForVerify()` (verify tab + immediate verification).
- KDE/Dolphin integration: three service menus installed under `${datadir}/kio/servicemenus` (Plasma 6 path): `firmadigitaleopen-signpdf.desktop` (`MimeType=application/pdf`, action **Firma PDF**), plus `firmadigitaleopen-signpades.desktop` / `firmadigitaleopen-signp7m.desktop` (`MimeType=all/allfiles`, actions **Firma PAdES** / **Firma P7M**). They invoke `firmadigitaleopen --sign-pades %f` / `--sign-p7m %f`. GNOME/Nautilus has no equivalent yet (would need a Nautilus extension); AppImage does not install system service menus.

## Packaging — Arch Linux (PKGBUILD)

- Repo-root `PKGBUILD` (1.0.0) + `firmadigitaleopen.install` script sharing `resources/firmadigitaleopen.desktop`/`.svg` and the same CMake install rules. Arch runtime deps: `qt6-base poppler-qt6 openssl libxml2` (Qt6 is monolithic there — no separate network/sql packages).
- `makepkg` sources straight from the git remote configured in `.git/config` (`git+ssh://git@git.tizbac.ovh/tiziano/firmadigitaleopencpp.git`). The proprietary Bit4id `.so` is committed, so the clone ships it and CMake bundles it; without it CMake's bundle guard still builds and packages, minus the token module. **`makepkg` must not strip the module** (default `strip` option would truncate `libbit4xpki.so` and break it — `C_Initialize` fails with CKR_GENERAL_ERROR), hence `options=('!strip')` in the PKGBUILD. Tests are NOT run by makepkg (`check()` absent): the ctest suites need untracked fixture data (e.g. `tests/data/test.pdf`) that git doesn't ship — use the Dockerfile for a full build+test. `firmadigitaleopen.install` refreshes desktop+mime DBs in `post_install`/`post_upgrade`/`post_remove`.

## GitHub Actions release workflow

- `.github/workflows/release.yml` builds on push of a `v*` tag or `workflow_dispatch`, producing the `.deb`, the `.rpm`, the AppImage and the Windows NSIS installer via the Docker stages (`package`, `rpm-pkg`, `appimage`, `win-package`) and attaching them to the GitHub Release (`softprops/action-gh-release`). ## Windows packaging (NSIS)

- `packaging/windows/installer.nsi` is built by `makensis` (Debian `nsis` package, native Linux, no Wine) inside the `win-package` Docker stage; `-DAPP_VERSION`, `-DSOURCE_DIR` and `-DOUT_FILE` are passed in. Output name: `firmadigitaleopen-<version>-win64-setup.exe`.
- It installs to `$PROGRAMFILES64\FirmaDigitaleOpen`, adds Start Menu/desktop shortcuts, writes the uninstall entry, associates **only `.p7m`** (claims it only when it has no owner) and adds Explorer context menus: `Firma PDF` under `SystemFileAssociations\.pdf\shell` (`.pdf`-specific) and `Firma PAdES` / `Firma P7M` under `*\shell` (all file types). `.pdf` is never registered in `OpenWithProgids`/as a default handler. `SetRegView 64` is used so the 64-bit shell sees the associations. The context commands invoke `firmadigitaleopen.exe --sign-pades "%1"` / `--sign-p7m "%1"`; plain-file invocation still opens the verification tab. It refuses to run on 32-bit Windows.
- `resources/firmadigitaleopen.ico` (multi-size, generated from the SVG) is used for the exe, the installer and the shortcuts; `resources/firmadigitaleopen.rc.in` is configured by CMake into a VERSIONINFO + icon resource for the executable.
- Wine smoke test (manual, not in CI): a Debian trixie container with `wine32:i386`, `wine64`, `Xvfb` and `x11-apps` installs the NSIS package silently (`setup.exe /S`) and starts the GUI under Xvfb; the main window appears, and `bit4xpki.dll`, Qt6, poppler and `qwindows.dll` are all loaded. Wine's `reg.exe` is 32-bit and cannot see the 64-bit keys written with `SetRegView 64`; inspect `$WINEPREFIX/system.reg` instead (the uninstall/App Paths/`.p7m`/context-menu keys are present there). Verification was exercised under Wine with a Linux-generated P7M + TSL: no TSL → `FIRMA NON VALIDA`; granted CA service in the TSL → `FIRMA VALIDA` with the TSL anchor; same TSL with the service status changed to `withdrawn` → rejected again.

## PKCS#11 quirks (do not "fix")

- **Windows ABI (crash fix):** Bit4id's Windows x64 module was built with **4-byte struct packing**. Its embedded Lua card-profile bridge walks `CK_ATTRIBUTE` arrays with a **16-byte stride**, reading `pValue` at **+4** and `ulValueLen` at **+12**; `CK_MECHANISM` is likewise 16 bytes. Passing native 24-byte structs made it dereference padding/pointer halves as a value pointer and length, crashing in its Lua hash table during `C_FindObjectsInit` (`bit4xpki!C_GetTInterface2+0x6799`). `pkcs11_abi.h` now has `CK_ATTRIBUTE_PACKED` / `CK_MECHANISM_PACKED`; `FnTable::packedAbi` is enabled for module paths containing `bit4` (override with `FDO_PKCS11_PACKED_ABI=0/1`), and both `getAttr()` and the `C_FindObjectsInit`/`C_SignInit` call sites use the packed structs for Bit4id. Non-Bit4 modules (OpenSC/SoftHSM) keep the native layout.
- **Windows struct sizes:** `CK_SLOT_INFO` and `CK_TOKEN_INFO` must be the **complete** PKCS#11 structs. Bit4id writes every field of `CK_TOKEN_INFO` (160 bytes with 4-byte `CK_ULONG` on Windows); the old truncated "MIN" struct was only 148 bytes and corrupted the stack when a card was inserted. `src/pkcs11_abi.h` has the full structs plus `static_assert`s pinning 104/160 (Windows/32-bit) and 112/208 (LP64) bytes. The DLL's count fields are 4-byte `CK_ULONG` (verified with a sentinel-buffer `C_GetSlotList` probe). Treat slot/token strings as blank-padded fixed arrays (`fixedString()`), never NUL-terminated C strings. Set `FDO_PKCS11_TRACE=1` to log every enumeration call and return value to `%TEMP%\fdo-pkcs11.log`. `FDO_PKCS11_MINIMAL=1` skips the token/certificate probe entirely (slot description only) as a diagnostic fallback. On Windows the module is deliberately never finalized/unloaded during the process lifetime (Bit4id notification thread vs `DLL_PROCESS_DETACH`); `CKR_CRYPTOKI_ALREADY_INITIALIZED` is accepted and `closeLibrary()` is a no-op on Windows, while POSIX keeps the normal lifecycle.
- Signer key/cert are located by `CKA_ID` **DS3, DS4, DS5, ...** (renewed tokens move the signature identity); the layer pairs key and certificate by identical `CKA_ID`, prefers a DSx pair, then a currently-valid certificate, then the latest expiry. The GUI shows certificate subject, `CKA_ID` and expiry under the slot selector and asks for confirmation before signing with a non-DSx or expired certificate. SoftHSM (no readable `CKA_ID`) still falls back to the first key/certificate pair.
- `sign()` in `src/pkcs11.cpp` tries both `CKM_SHA256_RSA_PKCS` (0x1051) and 0x40: this system's p11-kit/SoftHSM build encodes the mechanism as 0x40.
- SoftHSM's `C_FindObjects` requires a non-NULL `pObjectCount`; SoftHSM reports every virtual slot as `tokenPresent`, so real tokens are distinguished by having a certificate.
- For manual SoftHSM work, `SOFTHSM2_CONF` must be exported for every PKCS#11 client process (setup steps in README.md).

## Conventions

- Core error strings are in Italian (e.g. `"xref non trovata (xref stream non supportato)"` in `pades.cpp`); tests and README rely on them — keep them.
- Tests are plain executables with a `CHECK` macro, no framework; they print `OK`/`FAIL` lines and return non-zero on failure.
